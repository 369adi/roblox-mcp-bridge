# Reference: security and performance
Load it for: stopping exploiters, validating remotes, anti-cheat, lag, memory leaks, frame rate, making a game run well on phones

## What an exploiter can do
They control their own client completely: run any code there, read everything replicated to them (all of `ReplicatedStorage`, `Workspace`, their `PlayerGui`, every LocalScript and ModuleScript source they receive), fire any remote with any arguments at any rate, and move their own character anywhere because the client owns its physics.

They cannot: read `ServerScriptService` or `ServerStorage`, change other players' data directly, or run code on the server, unless your remotes let them.

So security is entirely about what the **server** accepts.

## Remote checklist (every handler)
1. **Type** of every argument (`typeof(x) == "string"`), including that numbers are finite (`x == x` rejects NaN) and integers where expected.
2. **Range and length**: clamp numbers, cap string length, cap table size. Never iterate an unbounded table from the client.
3. **Identity**: the first argument (`player`) is the only trustworthy one. Never accept a player, a UserId or a character as an argument to act on someone else unless that is the feature and it is validated.
4. **Ownership and state**: do they own the item, is the tool equipped, are they alive, is it their turn, do they have the currency.
5. **Distance and line of sight** for anything spatial: compare server-side positions with a tolerance.
6. **Rate**: a per-player cooldown using `os.clock()`. Drop extra calls silently.
7. **Instances from the client**: check `IsDescendantOf` the place they should be in; a client can pass any instance it can see.
```lua
local function rateLimited(bucket: { [Player]: number }, player: Player, interval: number): boolean
	local now = os.clock()
	if now - (bucket[player] or 0) < interval then return true end
	bucket[player] = now
	return false
end
```
Clear per-player tables in `PlayerRemoving`.

## Never
- A remote that takes an amount to give, a price, a damage number, a stat to set, or a function name to call.
- `loadstring` on anything from a client, or `require(id)` of an asset id you did not write: that is how backdoors work. If you find one in the place (`require` with a number, obfuscated code, a "free model" script fetching remote code), tell the user where it is and what it does; do not remove it without asking.
- Secrets (webhook URLs, API keys) anywhere the client can read. Server scripts only.
- Admin commands checked on the client. Check `UserId` against a server list.
- Trusting a value object or attribute the client can change. Client changes do not replicate to the server, so read state from the server's own copy, never from a client-sent echo of it.

## Movement cheats
- You cannot prevent speed or teleport on the client; you can detect on the server: sample `HumanoidRootPart.Position` every 0.5 s, compare distance with what `WalkSpeed` plus a generous margin allows, ignore legitimate teleports (flag them when your code moves the player), and act on repeated violations by moving them back, not by instant bans. False positives from lag are common: be lenient.
- For obby or race results, verify checkpoints were touched in order with plausible times, on the server.

## Performance: where time goes
- **Server**: scripts doing work every frame, physics on many unanchored parts, humanoids, large replication.
- **Client**: draw calls (part count, unique meshes and materials, transparency, shadows), particles, UI updates every frame, memory.
- Measure before optimising: ask the user what feels slow, read `get_console_output`, and look for the obvious loop first.

## Script performance
- Events over polling. One `Heartbeat` connection that updates many objects over one loop per object.
- Cache services and instance references outside loops. `FindFirstChild` and `GetDescendants` in a hot loop are the usual culprits.
- Throttle: most logic does not need 60 Hz. Run AI at 5 to 10 Hz, UI text updates at 10 Hz.
- Reuse instead of create and destroy (bullets, damage numbers): keep a small pool.
- Avoid creating tables and closures per frame. Use `table.clear`, buffers and `table.create`.
- Parallel Luau (Actors) only for heavy, separable work; not a first resort.

## Memory leaks
- Connections to an object that outlives the listener: disconnect on cleanup. Per-character connections must end when the character is removed.
- Tables keyed by players or instances never cleared.
- Instances parented to `nil` but still referenced; tweens and animation tracks loaded repeatedly.
- A simple pattern: one cleanup table per feature (`table.insert(cleanup, connection)`), one function that disconnects and destroys everything in it.

## Replication cost
- Do not put large folders of server-only assets in `ReplicatedStorage`; use `ServerStorage` and clone on demand.
- Send small remote payloads (ids, numbers), not whole tables every frame. Unreliable remotes (`UnreliableRemoteEvent`) for high-rate cosmetic updates.
- Many moving parts replicated from the server is expensive: let clients animate cosmetics locally.

## Rendering cost
- Anchor and merge what you can; fewer, larger parts. `CastShadow = false` on small or hidden parts.
- `StreamingEnabled` for big maps (see `world`). `RenderFidelity = Automatic` on meshes.
- Limit shadow-casting lights, layered transparent parts, and particle rates.
- UI: do not rebuild lists every frame; update only changed labels; `CanvasGroup` sparingly.

## Phones
- Assume a third of desktop performance and far less memory. Test with the device emulator. Keep particle counts and draw distance modest, and never rely on hover or right click.
